# 轻舟 LiteArk 权限说明

> 本文描述文件夹级权限的**规则模型、计算方式、配置入口与接口**，内容与当前代码实现一致（`PermissionService`、`GrantController`、`AdminController`）。
> 网盘侧的文件、上传、预览、共享能力见《[网盘功能说明](网盘功能说明.md)》。

## 一、设计原则

1. **权限挂在文件夹上，不挂在文件上。** 文件继承其所在文件夹的权限，因此规则天然覆盖该目录及其全部下级，后续新增的文件与文件夹自动沿用，不需要二次配置。
2. **实时计算，不复制规则。** 每次访问沿目录链自上而下取交集，配置改动立即生效，无缓存、无同步延迟。
3. **角色是默认载体，用户是例外。** 角色的目录规则即「角色默认文件夹权限」，角色下所有用户自动继承；需要单独调整某个用户时，才为其添加用户规则。
4. **默认拒绝。** 除资源所有者与超级管理员外，未被授权的目录**完全不可见**（列表不出现、接口 403），不存在「未配置即全放」。
5. **越权不可放大。** 下级只能在上层授权范围内收窄；普通用户授出的权限不超过自己在目标目录上的有效权限。

## 二、权限位与操作映射

权限共四位，顺序即界面展示顺序：

| 权限位 | 名称 | 覆盖的操作 |
|--------|------|-----------|
| `view` | 文件查看 | 列表与搜索命中、进入目录、在线预览（图片/音视频/PDF/Office/文本）、查看历史版本、下载缩略图 |
| `edit` | 文件编辑 | 在线编辑保存、重命名、删除到回收站、剪切（移出）、历史版本回滚 |
| `download` | 文件下载 | 下载原文件、批量 ZIP 打包（无下载权限的项在压缩包中自动跳过） |
| `upload` | 文件上传 | 上传文件（含分片上传）、新建子文件夹、粘贴复制、粘贴剪切（移入） |

**接口级校验位置**

| 接口 | 需要的权限 |
|------|-----------|
| `GET /api/files/list` | `view`（列表逐项过滤，无 view 的项不返回） |
| `GET /api/files/breadcrumb` | 逐节点按 `view` 判定，遇到无权限的节点即截断 |
| `GET /api/files/tree` | 无显式校验；树内只含自己的文件夹与可达的共享入口 |
| `POST /api/files/folder` | 父目录 `upload` |
| `PUT /api/files/{id}/rename` | 文件所在目录 `edit` |
| `POST /api/files/copy` | 目标目录 `upload` + 源项 `view` |
| `POST /api/files/move` | 目标目录 `upload` + 源项 `edit` |
| `DELETE /api/files?ids=` | 每项 `edit` |
| `POST /api/files/upload`、`/api/upload/init`、`/chunk`、`/complete` | 目标目录 `upload` |
| `GET /api/files/{id}/download` | `download` |
| `GET /api/files/{id}/preview`、`/thumbnail`、`/office-preview` | `view` |
| `PUT /api/files/{id}/save-text` | `edit` + 在线编辑开关 + 后缀白名单 |
| `GET /api/files/{id}/versions` | `view` |
| `POST /api/files/{id}/versions/{versionId}/rollback` | `edit` |
| `POST /api/files/download-zip` | 逐项判定 `download`，无权限的项跳过而非整体失败 |
| `POST /api/shares`（外部分享） | 共享根 `share_external`（非所有者也可，只要被授予该权限） |
| `POST /api/shares`（内部分享） | 共享根 `share_internal`，且 `targetIds` 至少一位站内用户 |
| `POST /api/grants`（用户自助授权） | 见第七章 |

> 历史权限位做了兼容归并：`delete` → `edit`，`share`/`read` → `view`，`write` → `edit`，`create` → `upload`。旧规则无需迁移即可继续生效；注意旧的 `share` 只等价于「查看」，**不等于**新增的 `share_internal`/`share_external`，需要分享能力必须单独勾选。

## 三、数据模型

单一表 `permission` 承载所有规则，唯一索引 `(subject_type, subject_id, folder_id)` 保证「同一主体 + 同一目录」只有一条规则，重复保存即覆盖。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER | 主键 |
| `subject_type` | TEXT | `user`（用户规则）或 `role`（角色默认规则） |
| `subject_id` | INTEGER | 用户 ID 或角色 ID |
| `folder_id` | INTEGER | 规则所在的文件夹 ID，必须指向真实存在的文件夹（根目录 0 不允许） |
| `perm_bits` | TEXT | 逗号分隔的权限位，如 `view,download,upload,edit` |
| `inherit` | INTEGER | 1 = 继承上级（默认）；0 = 阻断继承，该目录成为新的权限边界 |
| `source_role_id` | INTEGER | 仅用户规则使用。非空表示该规则按角色默认权限实时取值，此时 `perm_bits` 是**授权上限** |

`folder_id` 指向的目录被彻底删除时，其上的规则一并清理（`PermissionService.deleteByFolder`），不会留下孤儿规则。

## 四、有效权限计算

### 4.1 目录链

从目标文件夹向上回溯到根，得到一条**自根到当前**的链。回溯过程中一旦遇到「阻断继承」即停止向上。

> ⚠️ **阻断继承是目录级开关**，不是按主体生效：只要该目录上**任意一条**规则设置了 `inherit=0`，整条链在该目录处截断，对所有人都生效（包括角色默认权限的计算）。因此「单独授权某个子目录」的正确做法是——先在该子目录上给需要的人配置规则，再关闭该目录的继承开关，并确认该目录上的其他规则也符合预期。

### 4.2 每层取值优先级

对链上的每一层目录，按下表取该层的权限集合，取不到则沿用上级：

| 顺序 | 条件 | 该层权限 |
|------|------|---------|
| 1 | 存在该用户的规则，且带 `source_role_id` | `roleEffective(来源角色, 该层)` **∩** `perm_bits`（上限） |
| 2 | 存在该用户的规则，无 `source_role_id` | `perm_bits` 本身 |
| 3 | 无用户规则，但存在该用户所属角色的规则 | 角色规则的 `perm_bits` |
| 4 | 都没有 | 无规则（沿用上级，不参与交集） |

即：**用户规则优先于角色规则；按角色授权的用户规则，实际权限随角色默认配置实时浮动，但永远不超过当初设定的上限。**

### 4.3 交集

各层权限自上而下逐位取交集：

```
effective = layer_1 ∩ layer_2 ∩ … ∩ layer_n
```

空集代表「不可见」。例如父目录给 `view,download`，子目录配 `view`，则子目录内只能查看、不能下载。

### 4.4 文件、根目录与默认值

- **文件夹**取其自身计算出的权限；**文件**取其父目录的权限。
- `folderId <= 0`（本人根目录）不参与限制，返回全部权限；根目录下的文件也不参与授权，仅所有者可见。
- 目标不存在或已进回收站 → 空集。
- **超级管理员**（`role_id = 1`）恒为全部权限。
- **资源所有者**：若目录链上没有任何针对自己的规则，默认全权；一旦管理员为其配置了规则（例如仅 `view`），则按规则生效——这可用于限制所有者本人目录的下载/上传。
- **其他用户**：无规则即空集。

### 4.5 计算示例

设目录结构 `部门资料 / 合同 / 2026`，用户 U 属于角色 R：

| 场景 | 部门资料 | 合同 | 2026 | 结果 |
|------|---------|------|------|------|
| A. 仅在「部门资料」给角色 R 配 `view,download` | `view,download` | 沿用 | 沿用 | 三层均 `view,download` |
| B. 在 A 基础上给「合同」单独配 `view` | `view,download` | `view` | `view` | 2026 只剩查看 |
| C. 在 A 基础上给 U 配 `view,upload`（直接指定） | `view,download` | 用户规则优先：`view,upload` | 沿用 | 合同层 = `view,upload` ∩ 上级 = `view`（upload 被上级收窄，需上级给过 upload 才会生效） |
| D. 按角色 R 授权 U，上限勾选 `view` | 角色默认 `view,download` | 沿用 | 沿用 | 实际 `view`（角色默认 ∩ 上限）；角色后续加 `upload` 也不会放大 |
| E. 在「合同」上关闭继承并给 U `view` | 不再参与（被截断） | `view` | `view` | 合同层不再受「部门资料」约束，2026 继承合同的 `view` |

> 场景 C 说明：**用户规则本身也受上级约束**。用户规则不是「绕过上级的直通车」，只是在同层优先于角色规则。

## 五、角色默认文件夹权限

角色是文件夹权限的默认载体：配置一次、按岗位复用，人员新增或调岗自动跟随。

- **配置入口**：管理后台 → 角色管理 → 行内「修改权限」抽屉。
- **操作**：选择目录所有者 → 选择该所有者下的文件夹（可跨所有者，选择器为树形）→ 勾选六项权限（含内/外部分享）→ 保存。同一角色在同一目录重复保存即覆盖。
- **生效范围**：该角色下的全部用户（含后续新增用户）自动继承，规则同样递归覆盖全部下级。
- **角色默认权限的算法**：只沿目录链取**角色规则**的交集，不考虑任何用户规则（`roleEffective`）。该结果用于「按角色授权」时的实时取值、`role-effective` 接口查询与授权面板中的角色模板预览；角色抽屉里展示的是该角色的原始规则行，两者口径不同但一致收敛。
- **管理员角色不可配置**：`role_id = 1` 恒为全权，不作为模板出现在任何下拉中。
- **删除角色**：系统内置角色不可删除；角色下还有用户时拒绝删除。允许删除时，先清理该角色的全部默认规则，再把**引用它的用户规则**降级为「直接指定」并保留原 `perm_bits` 上限——不会因删角色而丢权限，也不会意外放大。

## 六、用户授权：两种来源

给具体用户加规则时，有两种来源，选择后不可混用（同一条规则只有一种来源）：

| 方式 | 存储 | 实际权限 | 适用场景 |
|------|------|---------|---------|
| **直接指定** | `perm_bits` = 勾选值，`source_role_id = NULL` | 固定为勾选值（仍受上级交集约束） | 一次性、临时性的单独授权 |
| **按角色授权** | `perm_bits` = 上限，`source_role_id` = 角色 | `角色在该目录的默认权限` ∩ `上限` | 希望该用户跟随岗位权限调整，同时保留一条不可逾越的天花板 |

按角色授权的语义细节：

- 勾选框表示**上限**而非最终权限，界面会实时显示「实际生效」。
- 角色默认权限调高 → 该用户同步获得（不超过上限）；角色默认权限调低 → 该用户同步收回。
- 若角色在该目录没有任何默认权限，则实际权限为空，该用户对该目录不可见——这是「按角色授权」的常见误配原因。
- 角色模板不能是管理员角色（`role_id = 1`）。
- 规则表与「我的分享」中，来源列显示 `角色 · 名称` 或 `直接指定`；按角色授权的规则在用户侧只读。

## 七、普通用户自助授权

文件夹所有者可以不经过管理员，自己把文件夹授权给同事。

**入口**

1. 进入自己拥有的文件夹 → 工具栏「授权」。
2. 文件列表行内操作 → 文件夹行「授权」（仅自己的文件夹出现）。
3. 移动端单项操作面板 →「授权给同事」。
4. 「我的分享」→「文件夹授权」区块：集中查看已授权对象、路径、权限、来源与继承状态，可**撤销**，也可「打开文件夹」跳转（`/files?folder=<id>`）。

**面板能力**

- 同事下拉可搜索，已授权者带标记，选中后回填其现有权限（不会误以为是追加）。
- 授权方式：直接指定 / 按角色；按角色时下拉显示该角色在本目录的默认权限与角色人数。
- 六项权限勾选（含内部分享/外部分享）+ 快捷预设（只读 / 可上传 / 全部）。
- 「继承上级权限」开关，关闭即在该目录形成新的权限边界。
- 已授权列表包含下级目录上的规则：本层规则可直接撤销；下级目录的规则标注「下级」，需到对应目录处理。

**约束**

| 约束 | 说明 |
|------|------|
| 仅限自己的文件夹 | 非所有者调用面板/授权/撤销一律 403；管理员走后台配置页 |
| 可授出 ≤ 自身有效权限 | 上限取 `effective(自己, 该目录)`；管理员若对所有者本人做了收窄，其可授出范围同步收窄 |
| 不能授权给自己 | 所有者本身已全权 |
| 不能授权给管理员 | 管理员已全权 |
| 根目录不可授权 | 根目录下的文件仅所有者可见，需先建文件夹 |
| 角色规则不可在此撤销 | 角色默认权限统一由管理员在角色管理中维护 |
| 目录彻底删除后规则随之清理 | 不留孤儿规则 |

## 八、管理端操作指引

### 8.1 角色管理 → 修改权限

| 字段 | 说明 |
|------|------|
| 目录所有者 | 先选人，再选其名下的文件夹（可跨所有者授权） |
| 文件夹 | 树形选择，只列文件夹，不列文件 |
| 六项权限 | 未勾选 = 该目录对角色不可见；不勾选分享位即不能发起对应类型的分享 |

### 8.2 文件夹权限页

| 字段 | 说明 |
|------|------|
| 授权对象 | 默认「角色」；需要单独调整某人时切「具体用户」 |
| 用户授权来源 | 「直接指定」或「按角色授权」（选择角色模板后显示其在本目录的默认权限与人数） |
| 文件夹 | 先选所有者，再从树中选择文件夹 |

## 九、可见性与数据归属

**可见性**

- 被授权的文件夹出现在被授权者的**根目录列表**与**左侧目录树**（树中标注 `文件夹名（所有者）`），列表行标注「某某 共享」。
- 只展示**入口文件夹**：若某目录的上级已可达，则不再重复出现在根目录，避免同一棵子树重复出现。
- 进入他人文件夹后顶部显示共享横幅与自身权限标签；按钮按权限收放（无 `upload` 不显示上传/新建，无 `edit` 不显示重命名/删除）。
- 未授权目录不返回、不报错；直接调接口返回 403。

**数据归属**

- 被授权者在他人文件夹内上传的文件、新建的文件夹，**归属该文件夹的所有者**，配额也计入所有者。
- 被授权者删除文件，进入的是**所有者的回收站**；回收站列表、还原、彻底删除、清空均只对所有者本人开放。
- 跨用户复制/移动受限（物理存储按所有者分目录），跨用户分享链接只能由所有者创建。

## 十、生命周期与级联清理

| 事件 | 处理 |
|------|------|
| 覆盖保存同一主体+同一目录的规则 | 更新原记录，`source_role_id` 可置空（用显式 `set` 更新，绕开 MyBatis-Plus 忽略 null 的行为） |
| 删除单条规则 | 直接删除，立即失效 |
| 文件夹彻底删除 | `deleteByFolder` 清理该目录上的全部规则 |
| 删除角色 | 先校验无关联用户 → `detachRole` 删除角色规则 + 将引用规则降级为直接指定 → 删除角色 |
| 用户被删除 | 由用户管理流程处理其文件与规则 |

## 十一、接口清单

**管理端（需管理员，`/api/admin`）**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/permissions?subjectType=&subjectId=` | 某主体（user/role）的全部规则，含路径、所有者、来源角色名 |
| POST | `/permissions` | 保存规则：`subjectType`、`subjectId`、`folderId`、`perms[]`、`inherit`、可选 `sourceRoleId` |
| DELETE | `/permissions/{id}` | 删除规则 |
| GET | `/permissions/effective?userId=&folderId=` | 查询某用户在某目录的有效权限 |
| GET | `/permissions/role-effective?roleId=&folderId=` | 角色在某目录的默认权限 + 角色人数 |
| GET | `/folders?ownerId=` | 指定所有者的文件夹树（含 path），供选择 |

**用户自助授权（需登录，`/api/grants`）**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/grants?folderId=` | 面板数据：`maxPerms`、`roles`（角色模板及本目录默认权限与人数）、`rules`（含下级目录规则）、`candidates` |
| POST | `/grants` | 授权：`folderId`、`userId`、`perms[]`、`inherit`、可选 `roleId` |
| DELETE | `/grants/{id}` | 撤销用户规则（拒绝角色规则） |
| GET | `/grants/mine` | 我授权出去的规则：路径、对象、实际权限 `perms`、上限 `cap`、来源角色、继承状态 |

**前端读取权限的接口**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/files/folder-info?folderId=` | 当前目录的 `perms`、`granted`、`ownerName`，用于收放按钮与共享横幅 |
| GET | `/api/files/list` | 每行附带 `perms` / `granted` / `ownerName` |

## 十三、边界与排障

**已知边界**

- 权限粒度到文件夹，不到单个文件；需要单独控制某个文件时，把它移入独立文件夹。
- 阻断继承是目录级开关（见 4.1），不支持「只对某个人截断」。
- 角色规则在用户侧不可撤销，需管理员在角色管理中停用/删除。
- 跨用户复制/移动仍受限（物理存储按 owner 分目录）。
- 越权上限来源是 `effective()`：管理员收窄所有者权限后，该所有者能授出的范围同步收窄，属预期行为。

**排障速查**

| 现象 | 排查顺序 |
|------|---------|
| 用户看不到文件夹 | ① 该目录是否有针对其本人或其角色的规则；② 规则是否被上级收窄成空集；③ 是否有一段链上 `inherit=0` 截断了本该生效的上级规则；④ 用「有效权限查询」核对 |
| 能看不能下载 | 检查 `download` 是否在上层被去掉；按角色授权时检查角色在该目录的默认权限是否含 `download` |
| 改了角色默认权限但用户无变化 | 该用户可能有一条**直接指定**的用户规则在生效（用户规则优先），或用户规则的上限不含新权限 |
| 按角色授权后用户不可见 | 角色在该目录没有默认权限（或超出授权者可授出范围），实际权限为空 |
| 上传按钮不显示 / 上传 403 | 当前目录缺少 `upload`；确认不是只读授权 |
| 规则删不掉 / 提示角色默认 | 角色规则需在角色管理中处理，用户侧只读 |
| 磁盘上还有文件但列表没有 | 归属所有者的目录被收窄或删除，检查 `effective` 与 `is_deleted` |
