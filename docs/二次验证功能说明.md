# 轻舟 LiteArk 二次验证（TOTP）功能说明

> 对应需求：`二次验证需求.md` V1.3  
> 实现版本：V1.1 增量功能（2026-11-27）  
> 适用范围：SpringBoot 2.7 + Java 8 + SQLite 单 fat jar 部署；兼容内网、信创离线环境。

## 一、方案结论

采用标准 TOTP（RFC 6238，HMAC-SHA1 / 6 位 / 30 秒步长），兼容 Google Authenticator、Microsoft Authenticator 等验证器。

需求中五项评审结论均已按确认项落地：

| 评审项 | 结论 | 实现 |
|---|---|---|
| 用户权限禁用策略 | 策略 A | 默认 A：禁止开通但保留已绑定，登录仍要求验证码；同时实现策略 B：禁用即清除密钥并解绑 |
| 管理员账号 | 不强制开启 | 管理员可不使用二次验证；若其本人已开启，敏感操作需先核验本人动态验证码 |
| 信任设备 | 增加 | 登录验证码页可勾选信任设备，有效期内免验证；用户可查看/删除 |
| 恢复码 | 可随时重生成 | 生成新批次时旧批次全部作废；恢复码一次性、用后失效、不自动解绑 |
| 绑定辅助核验 | 不需要 | 绑定时只校验验证器动态码，不依赖短信/邮箱/外部服务 |

管控仍为三级：**平台总开关 → 管理员单用户权限 → 用户自主绑定**。任一上级关闭时，用户不能新绑定/关闭；已绑定账号的登录校验不受总开关影响。

## 二、关键流程

### 2.1 登录

1. 账号密码校验通过后，后端查询用户绑定状态。
2. 未绑定：直接签发正式 JWT（原有流程不变）。
3. 已绑定：校验当前设备是否为有效信任设备。
   - 是：直接签发正式 JWT。
   - 否：返回 5 分钟有效的 `pendingToken`（`purpose=totp`），前端跳转独立 `/totp` 页面。
4. `/totp` 页面提交动态验证码；勾选“信任此设备”时，校验成功后写入信任设备记录。
5. 验证码连续错误达到阈值后临时锁定；锁定期内动态码不可用，但恢复码仍可登录，管理员也可重置。
6. 恢复码登录成功后仅标记该码失效，不解绑、不新增信任设备。

`pendingToken` 只放前端内存（Pinia，不写 localStorage），且 JWT 过滤器明确忽略该类型令牌，无法访问任何业务接口。

### 2.2 用户自助

入口：前台「我的 → 账号安全 · 二次验证」。无开通权限时模块隐藏。

- 开启：生成密钥 → 前端本地生成二维码并展示明文密钥 → 输入 6 位动态码校验 → 绑定成功并一次性展示恢复码。
- 校验失败：删除暂存密钥，不保留半成品绑定。
- 关闭：动态码或一条未使用的恢复码二选一核验，成功后清除密钥、全部恢复码与全部信任设备。
- 恢复码管理：随时重新生成，旧批次全部作废；展示页带用户与时间水印。
- 信任设备：列表展示设备名、IP、端类型、到期时间，支持单条删除；过期记录自动清理并写审计。

### 2.3 管理端

入口：后台「用户管理」「系统配置」「操作日志」。

- 系统配置：总开关、错误阈值、锁定时长、时间容错窗口、恢复码数量、禁用策略 A/B、信任设备有效期。
- 用户管理：列表展示“允许开通 / 禁止开通”和“已绑定”状态；支持单个和批量设置，批量操作有二次确认弹窗。
- 管理员本人已绑定 TOTP 时：修改他人权限、批量修改、重置二次验证前，必须输入管理员本人的动态验证码；重置场景允许用恢复码。
- 应急重置：清除目标用户密钥、恢复码与全部信任设备，写审计。
- 审计查询：复用「操作日志」页，类型下拉已加入全部二次验证动作，可按用户、时间、结果筛选并导出 CSV。

## 三、安全实现

| 要求 | 实现 |
|---|---|
| 密钥不明文存储 | AES-GCM 加密后存 `user_totp.secret_cipher`；主密钥来自 `liteark.totp-master-key`，未配置时由 JWT 密钥派生 |
| 恢复码不明文存储 | HMAC-SHA256（主密钥 + 用户 ID + 规范化恢复码）后只存哈希，明文仅在生成/重生成时展示一次 |
| 传输安全 | 生产环境应通过 Nginx 终结 HTTPS；涉及密钥、恢复码、验证码的接口禁止明文 HTTP 暴露 |
| 验证码重放防护 | 成功校验后记录 TOTP 步长 `last_used_step`，同一窗口内重复验证码被拒绝 |
| 暴力破解防护 | 失败计数落库；达到阈值锁定，锁定期内仅恢复码或管理员重置可通行 |
| 设备绑定 | 前端本地生成设备 UUID，经 `X-Device-Id` 上报；后端按“用户 + 设备标识”加盐哈希后存储，不保存原始设备标识 |
| 日志脱敏 | 审计只写业务语言；密钥、二维码 URI、恢复码、验证码、令牌均不写入日志 |
| 无外部依赖 | TOTP 计算、加密、二维码生成均在本地完成；不调用短信、邮件或在线二维码服务 |
| 前端不可绕过 | 权限判断、验证码校验、信任设备判定、锁定判断全部在后端；前端仅展示与转发 |

> 注意：修改 `liteark.totp-master-key` 会导致已绑定用户的密钥无法解密，需管理员逐个重置。请备份主密钥，不要与 JWT 密钥相同。

## 四、数据结构

新增配置默认值写入 `system_config`；`user` 表新增 `totp_allowed` 列（旧库通过 `DataInitializer.migrate()` 增量添加）。新增三张表：

- `user_totp`：用户 ID、密钥密文、启用状态、失败次数、锁定到期、最后成功步长。
- `totp_recovery_code`：恢复码哈希、使用状态、批次、使用时间。
- `trusted_device`：设备哈希、设备名、IP、端类型、创建与到期时间。

新库直接在 `schema.sql` 建最终结构；存量库启动时自动增量迁移，无需手工执行 SQL。

## 五、接口清单

用户端（均需正式 JWT，除标注外）：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/auth/totp/status` | 状态、权限、恢复码/信任设备数量 |
| POST | `/api/auth/totp/bind` | 生成密钥与 otpauth URI |
| POST | `/api/auth/totp/bind/verify` | 校验动态码完成绑定 |
| POST | `/api/auth/totp/unbind` | 身份核验后关闭 |
| POST | `/api/auth/totp/recovery/regenerate` | 身份核验后重生成恢复码 |
| GET | `/api/auth/totp/devices` | 信任设备列表 |
| DELETE | `/api/auth/totp/devices/{id}` | 删除信任设备 |
| POST | `/api/auth/totp/verify-login` | 临时令牌 + 动态码完成登录 |
| POST | `/api/auth/totp/recovery-login` | 临时令牌 + 恢复码完成登录 |

管理端（需管理员 JWT）：

| 方法 | 路径 | 用途 |
|---|---|---|
| PUT | `/api/admin/users/{id}/totp/allowed` | 单个设置开通权限 |
| POST | `/api/admin/users/totp/allowed/batch` | 批量设置开通权限 |
| POST | `/api/admin/users/{id}/totp/reset` | 应急重置 |

## 七、部署注意事项

1. 启用二次验证前必须通过 HTTPS 访问（内网可由 Nginx 自签证书终结 TLS）。
2. 服务器时间需与 NTP 同步，时间漂移过大会导致动态码校验失败；内网请配置内网 NTP 源。
3. 建议外置配置中单独设置 `LITEARK_TOTP_MASTER_KEY`（`openssl rand -hex 32`），并纳入备份。
4. 平台总开关默认关闭，存量用户默认未绑定，升级后无感知；管理员按需开启后再逐用户授权。
5. 二维码由前端 `qrcode` 包本地生成，无需联网；恢复码展示页建议提醒用户离线抄录。
