## 3. 缺陷修复记录

### DEF-001（严重，已修复）复制文件后彻底删除副本，导致原文件实体丢失

| 项 | 内容 |
|---|---|
| 发现用例 | M2-14 复制后彻底删除副本不影响原文件（V1.0 FAIL） |
| 回归用例 | M2-14（V1.1 PASS：复制 code=0；原文件下载 HTTP 200，内容完整） |
| 根因 | `FileService.copyOne()` 中副本直接复用源文件的 `storageKey`，两者指向同一物理实体；`permanentDelete()` 按 `storageKey` 物理删除时未校验其他引用。 |
| 修复 | 1) `copyOne()` 改为调用新增的 `copyPhysical()`：为副本生成独立 `storageKey` 并物理复制文件，目录/无实体文件返回 null；2) `permanentDelete()` 与 `clearRecycle()` 删除物理文件前统一走 `deletePhysicalIfUnused()`，查询 `file_meta` 中是否仍有其他行（含回收站中的行）引用同一 `storageKey`，有引用则只删当前记录、保留物理文件，兼容历史共享 key 的旧数据。 |
| 额外收益 | 副本与原件编辑互不干扰（原文件在线编辑直接写原 `storageKey`，此前会连带改写副本内容；修复后已隔离）。 |
| 验证 | 手动复现：复制 → 编辑原文件（源 `EDITED-CONTENT`、副本 `ORIGINAL-CONTENT`）→ 删除副本 → 原文件下载 200 且内容正确。 |
| 变更文件 | `src/main/java/com/liteark/service/FileService.java` |

### DEF-002（一般，已修复）共享访问记录接口未校验所有权，存在越权查看

| 项 | 内容 |
|---|---|
| 发现用例 | M5-18 越权查看他人共享访问记录（V1.0 FAIL） |
| 回归用例 | M5-18（V1.1 PASS：其他用户返回 code=403） |
| 根因 | `ShareController.access()` 直接调用 `shareService.accessList(id)`，未按 `ownerId` 或管理员身份校验。 |
| 修复 | `ShareController.access()` 增加三层鉴权：未登录 `currentUser.id()` 抛 401；共享创建者、文件所有者、管理员任一满足方可查看，否则抛 403「无权查看共享访问记录」。 |
| 验证 | 匿名 → HTTP 401/code=401；创建者 → 200/code=0；其他登录用户 → 200/code=403；管理员 → 200/code=0。 |
| 变更文件 | `src/main/java/com/liteark/controller/ShareController.java` |

## 5. 风险与建议

1. **历史数据**：V1.0 之前通过复制产生、仍共享同一 `storageKey` 的旧副本，虽然已在删除侧加引用检查兜底（删其一不会破坏其他引用），但其内容仍会随任一方的在线编辑而同步变化。如需彻底隔离，可在业务低峰期按 `storage_key` 分组扫描 `file_meta`，对共用 key 的文件逐条物理复制并更新 `storage_key`。
2. **代码与文档一致性**：《功能说明》中"跨用户分享链接只能由所有者创建"与代码实现（有权限的非所有者可创建）不一致，建议更新文档以代码为准。
3. **测试覆盖补充**：本次以接口测试为主，建议后续补充浏览器端 UI 交互、移动端适配及并发上传压测。
4. **部署提醒**：根目录历史 `LiteArk-V1.1-full-deploy-*.zip` 不含本次缺陷修复，正式出包需基于最新 `target/liteark.jar` 重新打包。
